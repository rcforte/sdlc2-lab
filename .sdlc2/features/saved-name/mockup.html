UX experience spec

Status: finalized in the ux node's arbiter (DECIDE) round. Rounds 1–2 produced everything below; the arbiter round re-verified it against feature.md, completed the variant labelling of the po node's preserved happy-path screens, and recorded the outstanding calls as VH-ux-01 and VH-ux-02 in VERIFY-WITH-HUMAN.md. Nothing below is blocked on a human: the developer can build from it as it stands.

1. Experience summary

Actor: the Visitor (feature.md Ubiquitous language) — same actor as greet-visitor, no new identity or account. Job-to-be-done: "let me hold onto the name I was just greeted as, so being greeted that way again never means typing it out a second time." Entry: the same single route this feature extends — / — always arriving with nothing saved (Story 5), whether it is the first visit or a later one. Exit: none inside this feature, same as greet-visitor — the visitor may loop (save, greet again, replace) indefinitely or leave the tab. Success metric: the visitor reaches a second "Hello, Ada" using only "Save this name" and "Greet me again" — zero retyping, zero instructional copy, using only the two fixed control names and the region's own text.

2. Primary flow — happy path and recovery

This feature does not replace greet-visitor's own ARRIVE / TYPING / SUBMIT / SUCCESS / ERROR flow (see that feature's own mockup.html) — it adds a second, parallel state machine for the Saved name region, whose transitions are triggered by, but independent of, the greeting flow. The two machines compose: every screen drawn above is one point in the greeting flow crossed with one point in the saved-name flow.

Saved-name states: NOTHING-SAVED (region reads "No name saved yet."; save control absent; greet-again control absent; hint absent) · SAVEABLE (a greeting exists but nothing is saved yet; save control has appeared; region still reads "No name saved yet."; greet-again and hint still absent) · SAVED (region and hint both read "Saved: <name>"; save and greet-again controls both present) · REPLACED (same shape as SAVED, reached by saving again — silently, no confirmation, per Story 4).

Every transition in the saved-name flow. "Trigger" is always something the visitor does. There is no state this table cannot reach or leave — every non-terminal state has a way out.

3. Information architecture & navigation model

  • Route: still / — the same single route greet-visitor established. This feature adds a region to that one screen; it does not add a screen, a sub-route, a modal, or a query parameter.
  • Deep-linking: every load of / renders NOTHING-SAVED (Story 5), identically to a first visit, because nothing here is persisted (feature.md Out of scope). No URL can land a visitor mid-flow; deep links stay trivially consistent, exactly as greet-visitor already established for the greeting itself.
  • "Where am I": unchanged from greet-visitor — the persistent <h1>sdlc2 lab</h1> is still the one fixed anchor. This feature adds a second, subordinate landmark under it: the Saved name region itself, exposed as role="region" with the accessible name "Saved name" (feature.md Contract vocabulary) — so "where am I, within the page" now has two answers instead of one: the page (via <h1>) and the region a visitor is currently reading or acting inside (via the region's own accessible name, reachable through landmark navigation in any screen reader).
  • "Where can I go": nowhere new — still no nav bar, no second page. The two new controls ("Save this name", "Greet me again") are not navigation; they act on this one screen's state and leave the visitor exactly where they were (feature.md: "saving does not move focus").
  • Landmark structure & DOM order: the Saved name region is a sibling of the existing form and status region, inside the same <main> — no new top-level landmark, consistent with greet-visitor's own choice not to introduce one. Document order is fixed and never reorders across any state: form → status region → Saved name region (feature.md: "the Saved name region appears after the status region"). See the landmark wireframe below.

5. Wireframes — ASCII block layout, primary action marked

The Saved name region drawn as a block, at its three distinct shapes. [ PRIMARY ] marks the one action a visitor is being steered toward at that moment within this region — a structural/interaction claim about which control is the obvious next step in the saved-name flow, not a visual-styling instruction. Every other control in the region is drawn plain, and there is never more than one [ PRIMARY ] per screen inside the region. This claim does not extend to "Greet me": that button, and its filled dark treatment (form button { background: #1a1a1a; ... }), predate this feature and belong to greet-visitor's own mockup — this feature does not reassign or contest its look. Which control reads visually louder than which, screen-wide, once both regions coexist, is frontend-design's call to make with real tokens; this spec fixes structure only.

6. A11y & responsive notes

  • Labels & names: the region has an explicit accessible name ("Saved name") via aria-label, not just a visual heading — so getByRole('region', { name: 'Saved name' }) and a screen-reader's landmark list agree. Both buttons carry their fixed accessible names as visible text content, never an icon-only control, never interpolated with the saved name (feature.md Decisions: "control names are fixed").
  • Heading order: the region's own heading is an <h2>, not an <h3> — greet-visitor never introduced a <h2> on this screen, and that absence is exactly why this feature's own new heading takes the next level down from the page's single <h1>, rather than skipping one. A gap in the heading tree (h1 straight to h3, nothing at h2) is what axe's heading-order rule and a screen reader's heading navigation both flag as broken; h1 → h2 has no gap to flag. feature.md fixes no heading level for the region, so h2 costs nothing to choose.
  • Keyboard path (tab order), unaffected by state: Name field → "Greet me" (submit) → "Save this name" (only once rendered) → "Greet me again" (only once rendered). Both new controls sit after the form in DOM order and are real <button type="button"> elements outside the <form> (feature.md Decisions), so Tab reaches them in that order and Enter/Space activates either — no custom key handling, no tabindex tricks, nothing a keyboard-only visitor has to learn that a mouse visitor does not.
  • Visible focus: both new buttons get the same :focus-visible outline as the existing "Greet me" button — outline: var(--focus-ring-width, 2px) solid #1a1a1a; outline-offset: var(--focus-ring-offset, 2px);, the same two normative tokens greet-visitor already fixed (--focus-ring-width: 2px, --focus-ring-offset: 2px), reused here rather than invented. A screen drawn with a control mid-activation (e.g. after "Save this name" is pressed) marks it with class="is-focused", a static, non-functional marker that renders the identical outline — never the autofocus attribute, which would move real focus on page load and contradict the seed's "saving does not move focus". Saving is the one moment this matters most: the seed requires focus to stay on "Save this name" after activation (feature.md: "the save control survives its own activation"), so the visible focus ring must still be showing on that same button immediately afterward, not reset to the document body.
  • Focus after "Greet me again" (ux-decided, no AC covers it — see VH-ux-02): feature.md fixes focus behaviour only for saving ("saving does not move focus"; Story 1's "Saving does not move focus" scenario, and Story 4's identical-replace scenario). No acceptance criterion says where focus goes after greeting again. This spec fixes it as the same rule: focus stays on "Greet me again" (drawn as s2d's class="is-focused"), which is simply what a native <button> does when nothing takes focus away — so it is the default a developer reaches by writing no focus code at all, and it never destroys the focused control (the greet-again button survives its own activation exactly as the save button does). The rejected alternative — moving focus to the status region so the new greeting is read — was rejected because the status region is already a live region and announces itself, and moving focus would strand a keyboard visitor away from the control they just used. Normative for the developer: do not call focus() anywhere in this feature.
  • Live region politeness, not shouted: the Saved name region carries aria-live="polite" (never assertive) so a save never interrupts anything already being read — consistent with greet-visitor's own status region. It deliberately does not carry role="status", to avoid a second element answering getByRole('status') in the already-merged greet-visitor suite (feature.md Contract vocabulary, "Announced" — VH-02 is the open human check on whether the bare attribute re-announces as reliably). feature.md's Contract vocabulary fixes aria-live="polite" directly on the outer role="region" element itself, not on an inner paragraph — so on the very first save (SAVEABLE → SAVED, e.g. s1b → s1c), the same DOM mutation that changes the region's text also inserts "Greet me again" as a new child of that same live region, and a screen reader may announce the whole of the region's new content, not the paragraph's text alone. This is an accepted, known shape for this feature's chosen live region — not scoped down to the paragraph only, because doing so would mean the region and the hint no longer share one attribute contract — and it is exactly what VH-02(f) below asks a human to confirm and record, alongside VH-02(a)-(e).
  • Never colour alone: every state above is distinguished by its text alone — "No name saved yet." vs. "Saved: Ada", the alert's own sentence, the hint's own sentence. No screen in this file uses colour, an icon, or a border style as the only signal of which state is showing; the neutral borders drawn in this lo-fi mockup are structural chrome, not a colour system (styling proper is frontend-design's call).
  • Description order is structural, not just visual: when both the alert and the hint describe the Name field, aria-describedby="name-error saved-hint" lists the alert's id first — the browser concatenates accessible descriptions in id-list order, not DOM order or visual order, so this is the one place order must be encoded in the attribute itself, not just in how the two paragraphs are laid out on screen (see s3d in Story 3, and the wireframe in section 3).
  • Touch target & contrast: both new buttons reuse greet-visitor's existing button styling, which already clears the 44×44px WCAG 2.5.5 target and the 4.5:1 AA text-contrast floor (see that feature's own mockup, section 6) — no new token is introduced.
  • Responsive: the Saved name region is block content in normal document flow, same single-column layout as the rest of the screen; it reflows with the page and needs no breakpoint of its own. It does not widen the page's existing max content width.

7. Handoff AC — the experience assertion the RTL/Vitest test must prove

A visitor who has just been greeted can find and use "Save this name" and, later, "Greet me again" using only the region's own visible text and the two controls' own fixed names — with no instructional copy anywhere on the screen, exactly as the acceptance criteria in feature.md already specify at the DOM level.
