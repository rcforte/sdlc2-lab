Experience spec (ux) — flow, IA and full state coverage

1. Experience summary

Actor: the visitor, alone on one screen, unchanged from greet-visitor and saved-name. Job to be done: "I'm sometimes Ada, sometimes Bob — let me hold onto both and switch without retyping, without one choice costing me the other." Entry: a fresh visit (page load), nothing saved. Exit: there is none — the visit simply ends (navigating away / reloading), and the next entry is another fresh visit (story 07). Success metric: a visitor who has saved more than one name can be greeted as any of them, at any point, without ever retyping a name they already typed once.

3. Information architecture & navigation model

Routes: one — /. This is deliberate, not an omission: the seed's "Out of scope" rules out persistence, so there is nothing to deep-link into that would still be there on arrival. The one honest route is the app root; "fresh visit" (story 07) is the deep link's landing state. No sub-route is invented to pad this section.

"Where am I / where can I go" without a route per state. Because every state is a re-render of the same single screen, "where am I" is carried by three landmarks that are always present, in every state including empty — the visitor can find each of them by landmark or heading whether or not it currently has content:

  • <header><h1>sdlc2 lab</h1></header> — the app itself (grounded in src/AppBanner.tsx, unchanged by this feature).
  • the <form> containing the Name field and "Greet me" — the Arrive/Greet step, always rendered, always the same fixed position.
  • role="status" — the Greeting, always rendered from first mount (even empty), per the existing "observed before its text arrives" rule this codebase already relies on.
  • role="region" aria-labelledby="…", headed "Saved names" — the new landmark this feature adds, always rendered from first mount, its heading text never changing across any state in the matrix below.

Where can I go, from any state: nowhere else — every control the visitor needs for every job (arrive, greet, save, greet-again, remove) lives inside one of these three always-present landmarks. There is no menu, no second page, no modal: the flat IA is the minimised-decisions principle applied to this feature. A screen-reader user who has never seen this screen before can jump landmark-to-landmark (header → form → status → Saved names) and know exactly what each one is for, in every state, because the landmark and its heading never move and never disappear — only their contents change.

A11y & responsive notes

Keyboard path (tab order), fixed regardless of state

  1. Name field
  2. "Greet me" (submit)
  3. each row, top to bottom, in save order — never resorted (Decisions: "a row never moves"): "Greet me again as <name>", then "Remove <name>"
  4. "Save this name" (only once there has been a greeting) — this is the last stop, so newly-saved rows always appear above the tab stop that created them, not after it

Focus management, one rule with no special case

  • Save: never moves focus. The button survives its own activation (React reuses the same DOM node; see V3's focus ring).
  • Greet again: never moves focus, for the same reason — it is an ordinary greeting, and the row's controls survive.
  • Remove: always moves focus to the Saved names region (tabindex="-1", programmatically focused), because the control that was pressed no longer exists to hold focus. One rule, applied whether or not the removed row was the last one (V5).

Labelling

  • Name field: a real <label for>, unchanged from greet-visitor.
  • Every row control's accessible name carries its own row's name — "Greet me again as Ada", "Remove Ada" — so a screen-reader user tabbing through five rows never hears five identical button names (Decisions: "row controls carry their name").
  • The Saved names region has both a visible <h2> and a landmark name, so the text a sighted visitor reads and the name assistive tech announces cannot drift apart.

Heading order (grounded in the shipped code, not invented here)

src/AppBanner.tsx already renders <header><h1>sdlc2 lab</h1></header>; src/GreetingScreen.tsx already renders the Saved-name heading as <h2> inside a labelled <section>. The real order is h1 → h2, one level, no skip. The mockup screens above use a decorative <p class="app-heading"> stand-in for the app banner — a convention the po's seven screens already established, kept unchanged here rather than introducing a second real <h1> into every one of twelve screens sharing this one HTML document (which would itself violate one-h1- per-document, a mistake specific to a multi-screen mockup file, not to the shipped app). The developer implements the real, single h1 → h2 order shown above; nothing here contradicts it.

Contrast & colour

  • Refusal / alert text #7a0000 on white ≈ 7.4:1 — passes AA at any size.
  • Hint / role-note text #333 / #595959 on white ≈ 12:1 / 7:1.
  • Focus outline #1a4fd6, 3px solid with 2px offset ≈ 5.2:1 against white.
  • Never colour alone: every refusal, alert and hint carries its meaning in text content and in an ARIA live region; row presence/absence is the only signal for "saved or not", never a colour swatch.

Reduced motion

No animation or transition exists anywhere in this feature (rows appear/disappear immediately; focus moves without any scripted scroll); prefers-reduced-motion has nothing to turn off.

Responsive

Single column, max-width: 640px, already reflows to any viewport ≥ ~320px without horizontal scroll; row controls wrap via the existing flex gap. Recommendation to the developer: keep each button's hit target ≥ 44×44px on touch viewports, since a row can carry two adjacent controls ("Greet me again as Ada" / "Remove Ada") that must not be easy to mis-tap for each other.

Handoff acceptance criterion

A first-time visitor, given no instructions beyond the on-screen copy, can: type a name and get greeted; discover "Save this name" only once greeted, activate it, and watch a labelled row appear while focus stays put; greet a second, different name and save it, and see both rows survive in save order (the walking skeleton, stories 01+02); use "Greet me again as <name>" on the first row to switch back without retyping, and watch the greeting re-announce; use "Remove <name>" on a row and land, by focus, in the Saved names region, which speaks its new contents; attempt to save a name already in the list and read, in that same region, that it is already saved with the list unchanged; fill the list to five, attempt a sixth, read the refusal that names its own way out, remove one, and then save the sixth successfully; and, starting a fresh visit, find none of it left over. Every step above is proven by the copy and the control names alone — no separate help text and no screen this document does not already show.
