The greeting log — mockup

One screen, extended: the existing labelled Name field and submit control ("Greet me"), the existing greeting (role="status"), the existing alert (role="alert", shown after a blank submission), and — new in this feature — the greeting log region headed "Greeted this visit" below it, plus a clear control that appears only once the log has an entry. Every block below is the same screen shown at a set of states, one set per story's happy path, drawn as before/after (or before/during/after) panels so the state each story changes is visible at a glance. This is a behaviour slice — no colour system, no visual design beyond what the existing markup implies; the neutral borders below are lo-fi structural chrome only. The clear control's label "Clear the log" is po-proposed, unconfirmed — see feature.md, Contract vocabulary, and VERIFY-WITH-HUMAN.md VH-01, VH-04 and VH-05 ("Clear the list" is the named alternative). Every greeting log region below is headed by a visible <h2> the region references via aria-labelledby, and is programmatically focusable (tabindex="-1") so focus can move there after clearing. The clear control is Story 2's own control — it is not drawn in Story 1's panels below, since Story 1's acceptance criteria never mention it (it "arrives with Story 2").

Experience spec — flow, states, IA, a11y

This section is the ux node's own artifact: how the screen behaves as a whole, not another drawn panel. It does not add screens, routes or controls beyond what feature.md already fixes — it is the map of the states and paths those panels below are samples of.

1. Experience summary

  • Actor. The Visitor — no account, no session, no identity beyond the text typed into the Name field (unchanged from greet-visitor).
  • Job-to-be-done. "Let me look back at everyone I've been greeted as during this visit, and let me wipe that log clean when I'm done with it."
  • Entry. Arrival at the (only) greeting screen — log empty, status region empty, Name field empty, no alert, no clear control.
  • Exit. None this feature adds. The visit — and everything this feature built during it — ends only when the visitor leaves or reloads (Story 3, "fresh visit"); there is no in-app "done" action beyond clearing the log itself.
  • Success metric. A visitor can name every greeting they have received this visit, in order, and clear the greeting log, in one activation each, without being told how — i.e. the Handoff AC in §7 holds unaided. (Round 2 fix, UX-MOCK: "that list" reintroduced a synonym the seed's Ubiquitous language explicitly rejects — "Not 'history'" — and VERIFY-WITH-HUMAN.md VH-04/VH-05 exist precisely to remove "list" drift from this feature's copy; "the greeting log" is used throughout this section instead.)

No navigational dead ends: every state above has at least one control that leads somewhere else on the same screen (submit, clear, or submit-again-to-dismiss-the-alert), and every state is reachable from ARRIVE by some path. The alert's only recovery is a further submission (unchanged greet-visitor rule) — clearing is deliberately not a way out of it (Story 2, "Clearing does not dismiss a pending alert"). Round 2 note (UX-FLOW): this is distinct from data loss. Activating the clear control is irreversible — feature.md Out of scope, "Undoing a clear": "Once Story 2's clear control is activated, the entries and the current greeting are gone; no story adds a way to bring them back." There is no confirmation step and no undo on a control whose own accessible name is still po-proposed, unconfirmed. Reaching a further, navigable screen state after clearing does not undo the loss of the cleared entries — see VERIFY-WITH-HUMAN.md VH-07.

3. Information architecture

  • Screen inventory. One screen: the greeting screen, route /. This feature adds no new screen and no new route — the greeting log is a landmark region inside the existing screen, not a page of its own. There is nothing to drill into per entry (seed Out of scope: "Removing, editing or re-greeting from an individual entry"), so there is no per-entry route to design.
  • Nav model. None — no nav bar, no tabs, no back button beyond the browser's own. "Where am I" is answered by the screen's own heading plus its two labelled regions (role="status", and the log region named "Greeted this visit"); "where can I go" is answered by the two controls on the screen (submit, and clear once it exists). Deep-linkability: trivially satisfied — the one route (/) carries no log-specific query or hash state, by design (seed Out of scope: "Persisting the log anywhere"; nothing survives a reload to deep-link into).
  • Landmark hierarchy (per screen) — round 2 rewrite (UX-IA). The shipped App.tsx already renders <main><header><h1>sdlc2 lab</h1></header>...</main> (greet-visitor's own landmark fix: one <main>, no second landmark). This feature adds the greeting log as a second landmark, nested inside that same <main>, as a sibling of the form and the status region — it does not sit outside <main> and it does not replace the existing single landmark. Concretely: <main> -> <header><h1>sdlc2 lab</h1></header> -> form (Name field + Submit) -> status region (role="status", unlabelled, not a landmark, still a plain sibling inside <main>) -> log region (role="region", named "Greeted this visit" via its own h2, also a sibling inside <main>, not nested inside the status region) -> clear control (<button type="button"> — normative, round 2 addition: never the implicit submit default, since the clear control lives in the same <form>-adjacent DOM as the Submit control and an untyped button would submit the form instead of clearing it — inside the log region, present only when the log is non-empty). No heading level is skipped (h1 then h2, never h3 without an intervening h2). Consequence for landmark navigation: a screen-reader user who was previously one landmark jump from "the whole page" now has two: jumping to <main> lands before the form as before, and a second landmark jump (region "Greeted this visit") skips straight past the form and the status region to the log — this is new with this feature and is the reason the log needs its own accessible name distinct from <main>'s. See the drawn DOM sketch below.

6. A11y & responsive notes

  • Heading order — round 3 fix (UX-A11Y), now matches this document's own emitted outline, not just the shipped app's. In the shipped app: h1 "sdlc2 lab" (the app's own title, in its <header>) -> h2 "Greeted this visit" (the log region's own accessible name, realized by a visible heading). No heading level is skipped; the status region and the alert are landmark-free and headingless by design, matching greet-visitor's own convention. In this mockup document, that two-level shape is nested one level deeper and repeated once per drawn state: the file's own single real <h1> ("The greeting log — mockup") is followed only by h2s (the experience-spec section, then one per story) and h3s (the experience-spec's seven subsections) — never a second <h1> — so each thumbnail's "sdlc2 lab" title is drawn as a non-heading, aria-hidden paragraph (.screen-title) rather than a competing <h1>, and each thumbnail's own "Greeted this visit" stays an h2, a sibling of the story h2 it sits under, not a child h3 — because in the real app it is an h2, sibling to the app's own single h1, and this mockup does not want to misrepresent that shape.
  • Landmarks. The log region is a role="region" landmark named via aria-labelledby pointing at its visible h2 — never an aria-label duplicating text that already exists on screen. The status region (role="status") and the alert (role="alert") are live regions, not landmarks, and are not part of landmark navigation.
  • Keyboard order (tab order = DOM order). Name field -> Submit ("Greet me") -> Clear control (only when present; it is the last focusable element, inside the log region, which follows Submit in DOM order) -> (loop). The log region itself is not in the tab order (tabindex="-1"): it only receives focus programmatically, once, immediately after Clear is activated.
  • Visible focus — round 2 fix (UX-A11Y), now drawn in CSS, not only asserted here. Every focusable control (Name field, Submit, Clear) keeps a visible focus indicator at all times — never outline: none with nothing in its place; this file's own <style> now demonstrates it too — input[type="text"]:focus-visible, button:focus-visible { outline: 2px solid #1a1a1a; outline-offset: 2px; } — reusing the two normative tokens greet-visitor/mockup.html already fixed: --focus-ring-width: 2px and --focus-ring-offset: 2px. The log region, though not tab-reachable, must also show a visible focus indicator when it receives programmatic focus after clearing — drawn here as .greeting-log:focus { outline: 2px solid #1a1a1a; outline-offset: 2px; }, deliberately :focus and not :focus-visible, because a script-driven .focus() call on a tabindex="-1" element does not match :focus-visible in Chromium — so a sighted keyboard user must still see where focus landed. Story 2's "after clearing" panel below carries a .demo-focus class that applies the same rule permanently, since a static document cannot hold real browser focus.
  • Never colour alone. Empty vs. non-empty log is distinguished by text content and DOM shape (paragraph vs. list), never by colour. The alert is distinguished by its role="alert" and its text, never by colour alone — consistent with greet-visitor's own "text, not colour" constraint (that feature's VH-07).
  • Contrast. Log entry text, the empty-log message, and the alert text each need to meet 4.5:1 against their background; the exact tokens are frontend-design's call, not invented here.
  • Responsive — round 2 fix (UX-A11Y), normative constraint replacing an untested claim. Single fluid column at every width, one breakpoint (none). Normative constraint: at a 320px viewport (WCAG 1.4.10 Reflow) no element on this screen causes horizontal page scrolling — the Name field and buttons are already box-sizing: border-box with fluid widths; the greeting, the alert and every log entry now carry overflow-wrap: anywhere; word-break: break-word; max-width: 100%; so a 300-char name (the carried, unretired no-length-limit AC) wraps inside its container instead of forcing the page wider; the §4 state matrix is wrapped in its own .table-scroll (overflow-x: auto) so a wide table scrolls inside its own box, exactly as greet-visitor/mockup.html already does for its own matrix.
  • Target size — round 2 addition (UX-A11Y). Every interactive control — Submit and the new Clear control alike — meets WCAG 2.5.5 (≥44×44px). Normative token for frontend-design: --control-min-target: 44px, drawn here as button { min-height: 44px; min-width: 44px; }.
  • Reduced motion. No motion is introduced by this feature (no animated list insertion, no transition on clear) — nothing to gate behind prefers-reduced-motion.

7. Handoff AC — what the RTL/Vitest layer must prove

Round 2 fixes (UX-MOCK, UX-A11Y): the heading named "Playwright," a tool this repo's CLAUDE.md rules out ("Deliberately not Spring Boot, Cucumber or Playwright") in favour of "React Testing Library + user-event via Vitest (jsdom)" — corrected above. Each item below is now restated as a DOM-observable assertion tagged with the feature.md scenario it proves, per this repo's own convention ("behaviour through the rendered DOM — roles and accessible names, never implementation details"); items that were previously unfalsifiable ("at a glance," "clearly labelled," "without being told where to look") are rewritten in terms of roles, accessible names and presence/absence instead.

  1. [S1 Sc1, Sc3] The greeting log region (getByRole('region', { name: 'Greeted this visit' })) contains an ordered list whose listitems' text content, read in DOM order, is exactly every name submitted this visit, oldest first — proving a visitor can read back every greeting without any assertion depending on visual position.
  2. [S1 Sc2, Contract vocabulary "two DOM shapes"] Whether the visitor has been greeted yet is distinguishable purely from DOM shape, not colour: empty is "no element with role list" plus the exact text "You have not been greeted yet."; non-empty is an <ol> of entries with that text absent — the two shapes are mutually exclusive, never layered, and the log never renders a count (seed Out of scope).
  3. [S2 Sc1, Sc2, Sc4, Sc6] The clear control (getByRole('button', { name: 'Clear the log' })) exists in the DOM only while within(logRegion).getAllByRole('listitem') is non-empty (queryByRole resolves to null otherwise), and expect(logRegion).toHaveFocus() holds immediately after it is activated.
  4. A blank or whitespace-only submission never silently corrupts the log or the on-screen greeting: the alert appears, and everything else — log, greeting, Name field — holds exactly still (S1 Sc6-Sc8).
  5. Clearing never dismisses an unrelated pending alert, and never touches the Name field's draft — only the log and the greeting move (S2 Sc5, Sc8).
  6. Leaving and returning (a fresh visit) always starts from the same clean slate as the very first visit — no entry, no clear control, ever survives across visits (S3 Sc1, Sc2).
