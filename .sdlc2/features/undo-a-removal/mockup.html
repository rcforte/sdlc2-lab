Undo a removal — happy-path mockup

One screen per user story's happy-path scenario (feature.md, User stories). Lo-fi, self-contained, no build step. Every control named by an acceptance criterion is present on its story's screen. The offer — a button reading "Bring <name> back" — sits between the "Saved names" heading and the rows, exactly where a refusal message already goes (seed, Agreed scope). The row controls carried over from earlier features — "Greet me again as <name>", "Remove <name>" — and the age reading and Newest marker carried from `saved-at` appear on every screen, since each one depicts the same finished Saved names region, only with different data.

ux node addition (round 1): the block below this paragraph is the experience spec — flow, information architecture, and the full state matrix — added by the ux node without touching the po node's four screens further down. After it, every screen (existing and new) carries a state badge naming which cell of the state matrix it is, and a "you are here / way out" nav note. Seven new screens are added, one labelled per state the po's happy-path set did not need to show: an offer standing over an emptied list, the offer at the five-name boundary in both directions, the over-limit refusal on its own, a replaced offer, an offer standing beside an unrelated field error, and the offer one tick before it ages out. No existing screen's markup changes.

1. Experience summary

Actor. The visitor — one person, carried unchanged from `greet-visitor`, `saved-name`, `remembered-names` and `saved-at`. No second persona exists on this screen.

Job to be done. Recover instantly from a mis-pressed Remove, without losing the name's saved-at moment or its place in the list, and without the recovery ever costing more than the one press that broke it (feature.md, Persona).

Entry. There is no separate entry point — the offer can only ever appear as a consequence of a removal the visitor themselves just performed, inside the one screen that already exists. There is nothing to navigate to.

Exit. Three ways, all designed, none a dead end: (a) the visitor presses the offer and the entry is back, whole; (b) the offer is superseded by something that actually changed the list — a further removal, a successful save, or a name falling off — and the screen returns to its ordinary state with nothing to press; (c) the held entry itself crosses the same day-old cutoff every row obeys, and the offer goes, silently. Every exit lands back on the one screen the visitor never left.

Success metric. A restored row is byte-for-byte the row that was removed — same text, same saved-at moment, same position, same (non-)Newest marker — reached in exactly one activation, with the rest of the screen (greeting, other rows, the limit) provably untouched. Story 01's scenarios are this metric, written as tests.

3. Information architecture

One route, one screen, always. The app is `src/App.tsx`: a single <main> mounting a banner and one GreetingScreen, no router, no persistence (seed, Out of scope). This feature adds no route and no screen — it adds a transient control inside the one landmark region that already exists. "Where am I" never changes; "where can I go" is answered by whichever finite set of controls the current state renders, never by a link elsewhere, because there is nowhere else.

6. A11y & responsive notes

  • Heading order. h1 "sdlc2 lab" (banner) → h2 "Saved names" (region). This feature adds no heading of its own — the offer is a button inside the existing h2's section, never a heading. (The mockup's own <h1 class="page-title"> and the <p class="app-heading"> per screen are documentation chrome standing in for the real app's h1; they are not part of the interface under design.)
  • Keyboard path. Name field → Greet me → [offer button, when present] → [Newest first, when rows > 0] → row 1: Greet-again, Remove → row 2: … → Save this name (when greeted). The offer sits before the sort control and the rows in both the visual order and the tab order — the same position (seed, Agreed scope) — so a keyboard visitor meets it before either. Remove is always the last stop on its row, one tab past Greet-again, on purpose (seed, Capability) — this feature does not change that order, it only adds one more stop before the rows.
  • Focus management. Two, and only two, programmatic focus moves exist on this screen: after a removal, and after a bring-back, both send focus to the region itself (tabindex="-1"), which then speaks its own new contents once. Nothing sends focus into a restored row — that would land a visitor one tab-stop from the Remove control that started this (feature.md, Decisions). A refused save leaves focus exactly where the click put it (the Save button), never moved.
  • Visible focus. The region's programmatic focus and the Save button's retained focus both get a 3px solid outline (.is-focused, already defined) — reused, not reinvented, on every new screen below that lands focus somewhere.
  • Never colour alone. The refusal is red text, but the words carry the refusal ("Five names is the limit…"), not the colour. "Newest" is a word, not a badge colour alone. The offer's button uses the same blue token as every other affordance in this file (#1a4fd6 / #eef4ff) — no colour is the sole carrier of any state anywhere on this screen.
  • Contrast. No new colour token is introduced by this feature; every value used above (#7a0000 refusal, #1a4fd6/#113a9c offer, #595959 secondary text) is already in this file's stylesheet and already documented there as meeting the 4.5:1 text floor.
  • Responsive. No discrete breakpoint exists or is needed: ul.rows li.row is already flex-wrap, so row controls wrap under the name at narrow widths without ever changing DOM order — keyboard/tab order therefore cannot diverge from visual order at any width. The offer button is a single inline element with the same fluid behaviour; it never needs its own breakpoint.

7. Handoff AC — what the end-to-end proof must show

  1. A visitor who mis-presses Remove can undo it in exactly one further press, with no instruction on screen or off it — the restored row is indistinguishable from the row before removal (text, saved-at moment, position, Newest/not).
  2. From every state in the matrix above there is a visible next action; nothing dead-ends. The single point with no automatic way back — the offer spent or aged out — always leaves the ordinary create-a-new-entry path (type → Greet me → Save this name) undisturbed and reachable; it is a designed stop for the offer, never a trap for the visitor.
  3. The offer, whenever present, precedes the sort control and every row in both the visual DOM order and the tab order, and is never reachable by a keyboard shortcut (seed, Out of scope: no global key handler exists or should be added).
  4. Focus after a removal and focus after a bring-back both land on the Saved names region, and its announced contents differ each time — proving the "announce once, never twice, never silently" rule holds across both triggers, not just one.
  5. A full list's refusal and a live offer are never observed together — provable directly from state 7's note: a successful save always ends whatever offer preceded it, so a refusal and a live offer never coexist (rows 6 and 7 differ only in which refusal, never in whether an offer is also live).
  6. No state anywhere signals success, refusal or "newest" by colour alone; each has accompanying text a screen reader or a forced-colours visitor also gets.
  7. The one true dead end — an aged-out offer — produces no message, no flash, no residue (story 03's own assertion): the E2E proof for it is an absence, not a presence.
