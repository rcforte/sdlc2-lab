Greet the visitor by name — mockup

One screen: a labelled Name field, a submit control ("Greet me"), a greeting (role="status"), and an alert (role="alert") when the name is blank. Every block below is the same screen shown at a different state, one per story's happy path, each carrying the existing "sdlc2 lab" heading that Story 1's acceptance criteria require to still be shown once the greeting screen's controls are added alongside it. The alert is text only — no colour-only signal is used anywhere in this mockup, per the feature's "error is text, not colour" decision (the human check for that constraint is VERIFY-WITH-HUMAN.md VH-07); the neutral borders on the error and greeting blocks below are lo-fi structural chrome only, not a colour system or visual design (see Out of scope in feature.md — this is a behaviour slice). The two regions behave differently when they have nothing to say, and the drawings below follow that exactly: the status region is always present in the DOM and simply holds no text — drawn, per the round 3 decision in section 4 (state matrix row 1), as a visually collapsed box with zero border and zero reserved space (not a dashed placeholder), with the explanatory caption outside it so the region itself really is textless — because a live region created at the moment its text arrives is unreliably announced; the alert is absent altogether when there is no error, matching "no element with role "alert" is present" (see feature.md, Contract vocabulary, and VERIFY-WITH-HUMAN.md VH-04). Correction (round 5, UX-STATE): trimming (" Ada " or a tab-padded "Ada" greeting Hello, Ada) does not produce exactly the plain "Ada" screen below — Story1-S3 requires the Name field to keep the raw, untrimmed value while only the greeting is trimmed, so the field and the greeting genuinely diverge. That divergence is drawn as its own variant in Story 1 below (state matrix row 4, tagged Story1-S3), because it is precisely the state a developer gets wrong by writing the trimmed value back into the field. The submit control is drawn here as a plain button, outside a <form>, purely as a lo-fi drawing choice — whether it belongs inside a <form> (which would also give Enter-to-submit) is an open question for a human, not a constraint of this mockup or this slice's acceptance criteria (see feature.md, Out of scope, and VERIFY-WITH-HUMAN.md VH-01).

UX experience spec

1. Experience summary

Actor: the Visitor (feature.md Ubiquitous language — no account, no session, no identity beyond the text they type). Job-to-be-done: "make this screen respond to me, not to everyone identically." Entry: any load of the single route (see Information architecture below) — always the same clean, empty screen, whether it is the very first visit or a later one (Story 4). Exit: there is no exit inside this feature — the visitor either sees a greeting and may repeat the loop with a new name, or leaves the tab; no navigation away is in scope. Success metric: the visitor reaches Hello, <name> in the status region using only the field's own label and the button's own name — zero instructional copy required anywhere on the screen.

2. Primary flow — happy path and recovery

Every state below is reachable from ARRIVE and every error state has a drawn way out; there is no dead end. Round 4 correction (UX-FLOW): the boxed ASCII diagram this section used through round 3 drew unequal box widths per state (the checker measured, e.g., a 68-column top border over a 17-column body on the SUBMIT box), which is exactly the "which edges enter/leave which box" information a flow diagram exists to carry, and prose could not fix that without a full redraw that risks drifting again. It is replaced below with five short state descriptions plus an explicit transition table — every row is from state, trigger, to state, AC — which cannot go out of visual alignment the way nested box-drawing can.

3. Information architecture & navigation model

  • Route: / — the Greeting screen. It is the only screen this feature adds, and the only route in the app. No sub-routes, no modal routes, no query parameters.
  • Deep-linking: / is idempotent and stateless — every load (first visit, reload, or a link shared with someone else) renders the identical ARRIVE state (Story 4), because the greeting and the alert are derived, never stored (feature.md Decisions). There is no URL that can land a visitor on a "broken" or half-drawn state; deep links are trivially consistent by construction.
  • "Where am I": the persistent, unchanging heading <h1>sdlc2 lab</h1> is the one orientation cue in the app and it is identical across every state in the matrix below — the one thing that never changes, so the visitor always has a fixed anchor regardless of what the status region or alert are doing.
  • Page title (round 5, UX-IA): the document <title> is the first orientation cue a screen-reader visitor or a visitor tab-switching between windows gets (WCAG 2.4.2 Page Titled) — it is the browser-chrome half of "where am I", complementing the in-page <h1> above. This mockup file's own <title> is "Greet the visitor by name — mockup"; the shipped app's title is App.tsx's existing document title (unchanged by this feature — the greeting is derived state, never a navigation, so there is nothing for the title to update to). Like the <h1>, the page title is identical across every state in the matrix below; a state change here is never a page change.
  • "Where can I go": nowhere else. There is deliberately no nav bar, menu, or secondary link — Out of scope rules out accounts and other screens, so there is genuinely nowhere else to go. The single control on screen (the submit control) is the single primary action everywhere; this is intentional one-action design, not an omission.
  • Landmark structure: one <main> region wraps the Name field, the submit control, the status region and (when present) the alert, so assistive-tech users can jump straight to the one thing on the page with a single landmark navigation. The shipped App.tsx already renders <main><header><h1>sdlc2 lab</h1></header></main>; this feature adds the Name field, the submit control, the status region, and (conditionally) the alert as siblings of the existing <header>, inside that same <main> — no second landmark is introduced. Nesting <header> inside <main> means it does not expose the implicit ARIA banner role (that role only applies to a <header> that is not a descendant of main/article/ etc.) — that is already true of the shipped app today and this feature does not change it; the heading order stays a single <h1>, no new heading level is introduced.
Landmark structure, drawn (arrive state) — resolves "where am I" structurally, not just in prose:

5. Keyboard path & focus order

Tab order: Name field → Submit control — two stops, total, in every one of the sixteen states above; no other focusable element ever appears, including in error states (the alert itself is not focusable, matching the standard alert pattern of being announced without requiring focus). Shift+Tab reverses the order. There is no keyboard trap in any state. Focus is never moved programmatically by this feature: it stays wherever the visitor put it — typically the submit control, immediately after activating it — because both the status region (aria-live="polite") and the alert (role="alert", implicitly assertive) announce their own content without needing a focus move. Moving focus on every submit would disorient a visitor who submits repeatedly (row 4, row 11).

Round 3 correction, rescoped round 4 (UX-STATE): "announce their own content without needing a focus move" is only reliably true when the live region's content actually changes at the DOM level — a live region is announced on mutation, not on click. Two cases in the state matrix above resubmit to an identical outcome (row 4a, submitting the same name twice; row 12a, failing the same way twice in a row) and, for those, a naive re-render that sets the same string risks being silent: nothing is announced, and a visitor who clicked "Greet me" again has no way to tell their click registered. The required fix is pinned at rows 4a and 12a as an outcome, scoped per result, not a blanket "mutate everything on every submit": on a successful resubmission (row 4a) only the status region must be made perceivable; on a failing resubmission (row 12a) only the alert must be — the other region is left completely untouched in both cases (row 9's "byte-for-byte unchanged" rule for a failing submit over an existing greeting is the reason this must not be a blanket rule: force-mutating the status region on a failing submit would re-announce a stale "Hello, <name>" as feedback for a submission that did not succeed, which is the opposite of what happened). The DOM mechanism (e.g. a keyed re-render, an explicit visually-hidden counter, content-swap timing) is deliberately left open for the developer/frontend-design node to choose — it is not prescribed here, and is not itself an acceptance criterion. See VERIFY-WITH-HUMAN.md VH-09 for the full options/decision record behind this requirement.

6. A11y & responsive notes

  • Labels: the Name field always has an explicit <label for> reading "Name"; the submit control always has the accessible name "Greet me" — identical across all 16 states above; nothing about a control's presence or name ever depends on state.
  • Never colour alone: the alert's meaning is carried entirely by its text and by the aria-describedby link to the Name field, never by colour or an icon alone (feature.md Decisions; human check recorded at VERIFY-WITH-HUMAN.md VH-07). This document uses neutral, colourless chrome throughout for exactly that reason — including its own drawn variants: the earlier "typing" screens used a yellow field tint to mark the draft state and that has been removed in round 3, because it was itself a colour-only signal inside a document asserting there is none. The typing state is distinguished only by its screen's text label ("Typing — draft, not yet submitted"); removing all colour from this mockup loses no information, which is exactly the VH-07 human check restated against this spec itself.
  • Programmatic association: aria-describedby on the Name field points at the alert's id whenever the alert is present, and is removed entirely — not merely emptied — whenever the alert is absent (row 11).
  • Landmarks & heading order: one <main>, one <h1> ("sdlc2 lab") per real render of the app — the before/after screen pairs drawn below are illustrative thumbnails of one screen at different moments, not literal nested headings in the shipped DOM.
  • Visible focus: every interactive element (Name field, submit control) needs a visible :focus-visible indicator meeting WCAG AA non-text contrast (3:1). Round 5 fix (UX-A11Y): this was asserted but not drawn, unlike the neighbouring target-size requirement, which had both a CSS demonstration and a named token. This file's CSS now demonstrates it too — input[type="text"]:focus-visible, button:focus-visible { outline: 2px solid #1a1a1a; outline-offset: 2px; } — and names two normative tokens for frontend-design: --focus-ring-width: 2px and --focus-ring-offset: 2px. Only the hue is left open; the structure (present, 2px, offset, ≥3:1) is fixed here.
  • Contrast: body text and alert text need 4.5:1 contrast against their background; the shipped UI's tokens/colours are frontend-design's domain, not fixed here. Correction (round 3, extended round 4): this document's own spec chrome is not colour-neutral — it invents one grey, #595959, used for the state-matrix "n/a" cells, the region-note captions, and (round 4) the .before-after .label caption that sits atop every one of the 16 drawn screens, all measured at ~7:1 against the white table/card background (comfortably clearing 4.5:1 for small text). Round 4 also gave .ac-tag an explicit #1a1a1a instead of letting it inherit — the chip sits inside labels and table cells with several different inherited greys, and an inherited colour is not a contrast guarantee. Every grey below 4.5:1 that this spec's own chrome used (#888 ~3.5:1/~3.09:1 depending on background, #777 ~4.48:1, both round 1/2) has now been replaced everywhere in this file, not only in the two spots fixed in round 3. No other hex values are introduced by this spec; every drawn screen's body text otherwise reuses the existing mockup's near-black #1a1a1a (already >7:1). Round 5 correction: the sweep above only covered text greys — this file's original input[type="text"] border was #999 on white (~2.85:1), below the 3:1 WCAG 1.4.11 non-text-contrast floor for a UI component's drawn boundary. It is now #595959 (~7:1), the same normative grey already used elsewhere in this spec.
  • Responsive: the single-column form reflows to full viewport width down to a 320px viewport (WCAG 1.4.10 Reflow — corrected in round 3 from an earlier, looser "~480px" claim) with no horizontal scroll at the page level, ever; the submit control keeps a ≥44×44px touch target at every breakpoint; no breakpoint changes the IA — it is still one screen, one action, at every width. This is the layout consequence of state matrix row 5 (a 300+ character unbroken name): the status region and the alert both wrap long unbroken tokens (overflow-wrap: anywhere; word-break: break-word, added to this file's CSS in round 3) and never truncate and never force a horizontal scrollbar — the box grows taller, never wider than its container. Correction (round 4): the 320px claim is the normative constraint the shipped screen must meet, and round 3's own drawing failed it — .before-after .screen had a bare min-width: 260px on a content-box element inside 2rem of body padding, which forced a page wider than 320px and than 375px. This file's CSS now demonstrates the constraint rather than merely asserting it: .screen is box-sizing: border-box, .before-after .screen uses min-width: min(260px, 100%) so it yields to a narrow viewport instead of overflowing it, and the 8-column state matrix below is wrapped in a .table-scroll container (overflow-x: auto) so it scrolls inside its own box the same way .flow-diagram already did, rather than the page scrolling.
  • Reduced motion: if frontend-design adds any transition for the alert or greeting appearing, it must be skipped under prefers-reduced-motion: reduce — no animation is required for the feature to function, so the default is no motion at all.

7. Handoff AC — the experience assertion for the RTL/Vitest test

Round 3 correction (UX-MOCK): this repo's declared frontend seam is "React Testing Library + user-event via Vitest (jsdom)" (project CLAUDE.md) and its own convention explicitly rules Playwright out ("Deliberately not Spring Boot, Cucumber or Playwright" — the graph tests node loops, not the rendered app in a real browser). The heading and the keyboard-only clause below are corrected to name that seam, not Playwright.

A visitor opens the greeting screen cold and, with no instructions: (1) locates the one labelled field and the one labelled action; (2) types a name, activates "Greet me", and sees Hello, <name> appear in a way a screen reader also hears without any focus move; (3) if they submit nothing (or only whitespace or tabs), see and hear exactly what to do next, with anything already on screen left untouched; (4) correct the mistake and succeed in the same visit, with no reload; (5) on a genuinely fresh visit, see the identical clean ARRIVE state as on the very first visit — nothing lingers; (6) resubmitting to an identical outcome (rows 4a, 12a) is still perceivable, not silent, at VERIFY time by a human (see the note below — that half is not suite-observable). The test suite should assert this using role-based queries only (getByRole, never a CSS selector), should walk every row of the state matrix above by asserting the status region's and alert's exact presence/text/ aria-describedby for that row, and should prove the full happy path plus the full recovery path are completable using only @testing-library/user-event's keyboard interactions under jsdom (Tab, type, Tab, {Enter}/{Space} on the button) — never a pointer-only or fireEvent-only shortcut for the primary path.

Correction (round 5, UX-STATE) — rows 4a and 12a are human-verified, not suite-asserted: every other row's presence/text/aria-describedby is a distinct, observable DOM shape a `getByRole`/`toHaveTextContent` assertion can walk. Rows 4a and 12a are different in kind: by construction their presence/text/aria-describedby are byte-identical to rows 4 and 12 (that identity is the entire point of the row — the risk is a silent re-render, not a wrong value), so a jsdom snapshot assertion of those same properties proves nothing beyond what rows 4/12 already prove. jsdom does not implement live-region announcement, so whether the second, identical outcome is actually perceived by a screen-reader visitor is unobservable under this repo's declared seam — the same class of gap VH-06 already named for storage writes. This requirement is therefore carried as a named human check at VERIFY time (VERIFY-WITH-HUMAN.md VH-09, human check named in VH-10), not as a thirteenth/fourteenth suite assertion alongside the sixteen state-matrix rows above.
