Saved at — UX spec & mockup

One screen per user story's happy-path scenario (feature.md, User stories), extended below with the flow, information architecture, full state matrix, and a labelled variant screen for every state the seed and the product brief describe. Lo-fi, self-contained, no build step. Every control named by an acceptance criterion is present on its story's screen. The two row controls carried over from remembered-names — "Greet me again as <name>" and "Remove <name>" — appear on every screen, since every screen here depicts the same finished Saved names region, only with different data.

1. Experience summary

Actor. The visitor — one person, one visit, carried unchanged from greet-visitor, saved-name and remembered-names. No second actor and no handoff between people exists in this feature.

Job-to-be-done. Know when each saved name was saved, trust that the answer stays true the longer the visitor sits on the screen, find the most recent save without reading every row, choose newest-first when that view is wanted, and never be confronted with a name saved and forgotten days ago (feature.md, Persona).

Entry. The screen mounts fresh — a new visit, empty saved-names list, no saved-at moment anywhere yet (seed, Out of scope: Persistence — nothing survives a reload, so every entry is this same empty state). There is no other entry point: no URL parameter, no onboarding step, no prior screen.

Exit. The tab closes or reloads. This is a deliberate, seed-mandated dead end for the visit (state is not carried anywhere) — it is not a UX dead end, because nothing on screen ever asks the visitor to go anywhere else to finish a task. Every task this screen offers completes on this screen.

Success metric. A visitor can answer "which name did I save most recently, and how long ago was that" by looking at the screen, without doing arithmetic and without reading documentation (feature.md story 01's own framing). The Handoff AC below turns this into the assertion the end-to-end test proves.

Information architecture & navigation model

One screen, one route. This is a single-page, single-component experience — there is no router, no second route, and (seed, Out of scope: Persistence) nothing to deep-link back to, since a reload always lands on the same empty entry state. "Where am I" is answered the same way on every state of this one screen: the page's own <h1> (app shell, unchanged by this feature) plus the <h2> "Saved names" landmark that names the one region this feature touches. "Where can I go" is answered by the controls visible in that state — never by a link to another screen, because none exists.

Sort view is UI state, not a route — deliberately. The seed's own words, "sorting is a view, not a reordering," apply doubly here: newest-first is not a place the visitor navigates to, it is a lens over the one place they already are. It is not deep-linkable and is not meant to be; giving it a URL fragment would imply a destination that contradicts "the visit goes on holding names in the order they were saved" (seed, Agreed scope).

Screen inventory (one entry, many states):

  • Saved names screen (route /) — the Name field, the status region, and the Saved names region. Every state in section 3 below is this one screen with different data and, in two cases (blank-name, full-list), a different message. No second screen exists in this feature.

2. Primary flow — happy path and recovery

Step-by-step, left to right through the story map (feature.md), with every recovery path shown as a branch back onto the same screen — never off it. 

[mount] --> Saved names region: EMPTY ("No names saved yet.", no sort control, no marker)
   |
   | visitor types a name, activates "Greet me"
   v
 blank? --yes--> alert "Please enter your name." (unchanged, carried) --> back to Name field
   | no
   v
status region: "Hello, <name>" --> "Save this name" control appears
   |
   | visitor activates "Save this name"
   v
 already saved? --yes--> region: "<name> is already saved."
   |  no                  saved-at moment, marker, sort position, 24h clock: ALL unchanged (PO decision: keep)
   |                       -----> visitor greets/saves a DIFFERENT name, or removes this row first
   v
 list at 5? --yes--> region: "Five names is the limit. Remove one to save another."
   |  no                 -----> visitor removes a row, or waits for one to fall off (story 04)
   v
row added: saved-at = now, age reads "saved just now", marker moves to this row,
row takes its place in both sort views (oldest-first default; newest-first if checked)
   |
   +--> (unprompted, every <=60s while mounted) age reading recomputes from the same
   |     saved-at moment: "saved just now" -> "saved 1 minute ago" -> ... -> "saved 1 hour ago" -> ...
   |     stable absolute time in the accessible name never moves.
   |
   +--> visitor checks "Newest first" -> display reorders newest-to-oldest; hint text
   |     ("Saved: ...") stays save-order; unchecking restores oldest-first. No data changes.
   |
   +--> visitor activates "Remove <name>" -> row leaves, focus moves to the region,
   |     region announces new contents, marker re-derives if the removed row wore it,
   |     a slot frees for another save.
   |
   +--> (unprompted, 24h after THIS row's own saved-at moment) row falls off on its own:
         region announces new contents exactly as a removal would, marker re-derives,
         a slot frees, but focus is left exactly where it already was (no control was
         pressed for the visitor to lose their place from).
   |
   v
 list empty again (every row removed or fallen off) --> back to EMPTY state at the top

No dead ends: every branch above either lands back on this same screen with a message and a working control, or produces the success row. The two refusals (duplicate, full) are pure recoveries — nothing is lost, the visitor's next action is always available on screen, and both are the two error states this screen has. The empty state is reachable from mount and from removing/aging out the last row, closing the loop.

Story 01 — Every saved name shows when it was saved, and the reading stays honest (walking skeleton)

Scenario "Two rows' age readings are independent". Ada was saved two minutes ago, Bob just now. Each row's age reading is its own words, in the words a person would use — never a raw timestamp. The small italic text under each name is the row's stable absolute time: in the real app it is not visible on screen, it is what a screen reader hears in the age reading's place, shown here only so a reviewer can see what it says.

3. State matrix

One screen (the Saved names screen, IA above), every state it can be in. "Loading" has its own row rather than being silently skipped: this screen makes no network call and persists nothing (seed, Out of scope: Persistence), so every transition below — greet, save, remove, toggle sort, a row aging out — is synchronous local state. There is no request for a spinner to cover.

4. A11y & responsive notes

  • Row accessible name carries the stable absolute time, never the ticking words. Structure: the visible ticking text (.row-age) is aria-hidden="true"; a second, visually-hidden node per row (e.g. a <span> clipped with a standard visually-hidden technique, referenced by the row's aria-label or aria-describedby) carries "<name>, saved <stable time>" and never changes on a tick. This mockup renders that node visibly (italic, muted) only so a reviewer can read it — production hides it exactly as a visually-hidden utility hides anything else.
  • Sort toggle must not read as a list write. The Saved names region carries aria-live="polite" on the whole section (unchanged, carried). Reordering the <ul>'s DOM children when "Newest first" is toggled risks the live region re-announcing the entire list, which the seed explicitly reserves for real writes ("a row falling off is a write to the list... it does not exempt the list from reporting that it changed" implies a view change is NOT such a report). Developer guidance: prefer CSS order on flex/grid rows over DOM reordering, or keep the toggle's target outside the live subtree, so checking/unchecking the box is silent the way scrolling would be.
  • Never colour alone. The "Newest" marker is a text label, read by any screen reader as ordinary content — the blue box shown in these mockups is a visual reinforcement, not the signal itself. Refusals ("...is already saved.", "Five names is the limit...") are text, not colour-coded status alone. The existing .role-note comment already flags #888 vs #595959 for the AA 4.5:1 text floor; the same check applies to whatever token frontend-design assigns the marker's border/text colour — verify it against white at 4.5:1, this spec does not invent the hex.
  • Keyboard order (tab sequence), top to bottom: Name field → "Greet me" → "Newest first" checkbox (only when it exists) → for each row, in display order: "Greet me again as <name>" → "Remove <name>" → "Save this name" (only when a greeting is current). The row's name text and age/time text are not focusable — they are read as part of the row's accessible name via labelling, not as separate stops.
  • Visible focus. Every interactive control (field, checkbox, both row buttons, both form buttons) gets a visible focus ring — this mockup's existing .is-focused outline (3px solid, 2px offset) is a shape/outline change, not a colour-only change, so it survives forced-colours and greyscale review.
  • Focus is only ever moved deliberately. Manual removal moves focus to the region (carried, unchanged — tabIndex=-1, ref.current.focus()). Greeting again and saving leave focus exactly where the visitor's own click left it. A row falling off on its own moves focus nowhere — the one state in this feature where "no focus movement" is itself the acceptance criterion (story 04).
  • Heading order. One <h2> ("Saved names") under the page's own <h1> (app shell) — unchanged, no level is skipped, and this feature introduces no new heading.
  • Reduced motion. The only thing that "moves" here is text content (the age reading's words, a row appearing/disappearing). No animation is introduced by this feature; nothing here needs a prefers-reduced-motion guard because nothing here motion.
  • Responsive. The existing row layout already wraps (flex-wrap: wrap on .row and .row-left) — below ~480px the name, age reading and marker stack above the row's two buttons rather than truncating. No new breakpoint is required by this feature; the state variants below reuse the same 640px story width as the product owner's four screens.

5. Handoff AC — the experience assertion the end-to-end test must prove

A visitor, with no instruction beyond what is on screen, can: save a name and watch its row read "saved just now"; leave the tab open and watch that reading advance on its own — "saved 1 minute ago", then "saved 1 hour ago" — without touching anything; look at the list, in either sort order, and identify the most recently saved name from the "Newest" label alone; check a single labelled control ("Newest first") and see only the display order change, proved by the Name field's hint staying in save order underneath; and, given enough elapsed time, watch a stale name leave the list on its own, with the region reporting the change exactly as it would for a manual removal and with focus undisturbed. A screen-reader visitor reaches the same three facts — when a name was saved, which name is newest, that a row changed — through a stable absolute time and the region's own announcements, never through the ticking words, which are hidden from them by design.
